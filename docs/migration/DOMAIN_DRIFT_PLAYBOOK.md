# Domain drift playbook (Phase 10.8)

## Что считается drift

- За окно (например 30 дней) проект имеет две половины: «предыдущая» и «текущая».
- В предыдущей половине доминирует домен A, в текущей — домен B, причём A ≠ B.
- В обеих половинах достаточно задач (порог в heuristics), иначе состояние weak_signal.

## Когда реагировать

- **Ожидаемая смена** — проект переключили на другой тип работ (например с legal на finance). Drift в этом случае информативен, но не требует исправления.
- **Неожиданная смена** — проект должен оставаться в одном домене, но задачи стали триажиться в другой. Стоит проверить: новые формулировки задач, качество routing_keywords, нужен ли override на уровне проекта.
- **Мало задач** — в одной из половин 1–2 задачи могли дать случайную смену. Смотреть task_count_previous / task_count_current; при необходимости увеличить окно или не считать это проблемой.

## Действия

1. Открыть проект: Dashboard → Проекты → проект или /owner/project/{key}, блок «Domain lifecycle».
2. Посмотреть reason и previous_dominant_domain → current_dominant_domain.
3. При необходимости: уточнить домен для задач (override), или отправить в refinement backlog предложения по реестру (ключевые слова, алиасы).
4. Telegram: /project_lifecycle &lt;key&gt; для краткой сводки, /domain_lifecycle — топ дрифтующих по портфелю.
