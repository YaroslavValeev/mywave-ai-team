# Role vs domain relation (Phase 9.9)

Почему role и domain — разные оси и как их использовать вместе без смешивания.

---

## Почему role ≠ domain

- **Role** отвечает на вопрос **кто смотрит / кто действует**: owner, operator, executor, reviewer. Это про права доступа, срезы данных и разрешённые действия (action center). Определяется конфигом/выбором view/allowlist.
- **Domain** отвечает на вопрос **какая экспертиза нужна задаче**: юридическая, аналитическая, разработка, маркетинг, продажи и т.д. Это про содержание задачи и подходящий контекст для рекомендаций, triage и промптов.

Роль не предопределяет домен, и домен не предопределяет роль. Один и тот же owner может работать с задачами из разных доменов; один домен (например legal) может быть релевантен и для owner (принятие решения), и для reviewer (ревью решения).

---

## Как они пересекаются

- В **role-based views** показываются срезы по роли (что видит operator, executor, reviewer). Домен задачи может использоваться для **фильтрации** или **подсветки** (например «задачи, требующие юридической экспертизы») без изменения прав.
- В **action center** разрешения привязаны к роли; домен может влиять на **рекомендуемые действия** или подсказки (например «для этой задачи доступен контекст legal»), но не на право выполнить действие.
- В **triage и routing** домен подбирается по тексту задачи; роль пользователя не меняет сам факт подбора домена, но может влиять на то, **какой срез контекста** показать (owner — полный контекст, executor — только actionable).

---

## Как future system может использовать их вместе

- **Domain-aware recommendations:** «Вам как owner рекомендуем обратить внимание на задачи с доменом legal: 3 в очереди решений.»
- **Role + domain в одном view:** Страница «Мои задачи» с фильтром по домену и срезом по роли.
- **Prompt/context auto-selection:** При формировании подсказки для агента подставляется context pack по домену задачи; права на действие по-прежнему проверяются по роли.

---

## Почему нельзя смешивать permission layer и expertise layer

- **Permissions** должны проверяться единообразно (action_center, require_owner_key, is_owner). Если в эту проверку встроить «экспертность», появятся неоднозначности: может ли «эксперт по legal» выполнять действие, доступное только owner?
- **Expertise** — только контент и рекомендации. Решение «кто что может делать» остаётся за role/action; домен лишь обогащает контекст и объясняет, какой тип экспертизы нужен задаче.

Итог: role и domain — две независимые оси; в коде и контрактах они не подменяют друг друга.
